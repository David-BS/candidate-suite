# Tracker format: source CSV + dashboard

## Data source: a CSV in the project files

An `Applications_Tracker_YYYYMMDD_HHMM.csv` file kept in the **project
files** (no Google Drive, no connector). The **name's timestamp is
authoritative**: on each update, a uniquely timestamped file is regenerated
and the user replaces the old one (see "Write ritual"). No timestamped
header inside the content — the name carries the version.

> **Exact name format (built by the script).** Date **without dashes**, time
> as `HHMM` **with no separator**: e.g. `Applications_Tracker_20260530_1728.csv`.
> **`manage_tracker.py` generates this name itself** when given `--output-dir`;
> it **prints the chosen path**. Dash-free format: aligned with the normalization
> the Claude app applies when indexing CSVs in a project (observed 30/05).
> Sorting by name and finding the "most recent" rely on this format.

### Columns (fixed order)

| Column | Description |
|--------|-------------|
| date | "YYYY-MM-DD" — **first activity** date (row creation); **preserved** on merge; used for sorting (descending by default) |
| company | Company |
| position | Exact job title |
| language | The **confirmed offer/letter language** (not a display or profile language) — read on resume for silent reuse (SKILL STEP 4, sub-step 3-bis). `"FR"` / `"EN"` today; an open ISO 639-1 code once per-language assets exist (L6). |
| status | Applied (default), Interview scheduled, In progress, Offer, Rejected, Withdrawn |
| deliverables | Types of produced deliverables, **accumulated** (union), separated by " ; " |
| conversation | **Multi-value**: one dated marker per conversation, accumulated, separated by " ; " (see "Marker states") |
| title | **Real title** of the most recent linked conversation, captured/rewritten at **reconcile** (DRV-5). A **display** field (desktop marker), **never a key**. Empty until a reconcile has captured a title. |
| notes | Free text |

### Conventions

- **Write key**: (company, position), normalized. **The date is NOT in the
  key** — the same application resumed on another day stays the same row. The "is this
  really the same application?" question is decided by the **assistant** (which asks when
  in doubt), not by a rigid key; the script provides the mechanical target.
- **Accumulative fields** (`deliverables`, `conversation`): merged as a **union**
  (case-insensitive dedup, first-appearance order), never overwritten.
- **Date**: preserved (first activity) — a later run doesn't overwrite it.
- **Other fields** (language, status, notes): overwritten by a non-empty value
  (the default status `Applied` never overwrites a real existing status).
- **CSV escaping**: native (`csv`), quotes around fields with commas/newlines.
- **Sort**: date descending, then company.
- **Zero connector**: `manage_tracker.py` only manipulates the CSV content.

### States of a conversation marker

The `conversation` column stores, per application, one or more dated markers
`YYYY-MM-DD` (date only, **no time**), each in one of three states:

| Stored form | State | Meaning |
|-------------|-------|---------|
| `2026-05-28 ◆` | **current / not yet linked** | produced in a conversation, link not yet set (written this way by `add_to_tracker`) |
| `2026-05-28 → {uuid}` | **linked** | the conversation's UUID is known (set by the refresh) |
| `2026-05-28 ✗` | **deleted** | the linked conversation is gone, link invalidated (set by the refresh) |

> **No time in the marker.** The dashboard cell only shows `MM-DD` anyway; the `◆` state alone removes any ambiguity about the current conversation, even if several links carry the same date. Adding `HH:MM` brings nothing to the screen and only opens a door to literal-template errors.

We store the conversation's **UUID** (not a full URL): the rendering builds the
URL if needed. Lifecycle: `◆` → `→ {uuid}` (at refresh, which finds the
conversation) → possibly `✗` (if it is later deleted). See the GUIDE for
reconciliation (DRV-5).

> **Language-agnostic glyphs (DRV-9).** `◆` (current / not yet linked) and `✗` (deleted);
> the linked form `→ {uuid}` is unchanged. The glyphs were chosen to collide with neither
> the CSV separator `,`, the intra-cell separator ` ; `, nor the arrow. The parser is
> **glyph-only** since the CSV migration to English-canonical: the former French tokens
> `(ici)` / `(supprimée)` are no longer read (legacy backward-compat dropped). Because the
> glyphs are mute, the dashboard **legend is mandatory**.

## Dashboard (interactive HTML)

Generated by `build_dashboard.py` from the CSV (or from JSON data in ephemeral
mode). Displayed inline via the visualization tool. Components:

- **Header**: "Usage guide" and "↻ Refresh from conversations"
  (`sendPrompt` buttons; visible labels localizable — see Localization below).
- **Counters**: Total, Applied, Interview, Offer.
- **2 donuts**: breakdown by language, by status (Chart.js).
- **Table**: sortable (header click), columns Date / Company / Position / Language / Status (+ Link if available).
- **Filters**: text search, status, language — local/instant.
- **Link column (multi-value)**: one dated marker per conversation, rendered according to
  its state **and the surface**:
  - **linked**, **web** surface → clickable `https://claude.ai/chat/{uuid}` link (new tab, same account);
  - **linked**, **desktop** surface → **marker to find/copy in the sidebar** (text selectable in one click): the conversation's **real title** (`title` column, captured at reconcile) if known, **otherwise** the built marker `📋 YYYY-MM-DD - Company - Position` (a link would go to the browser);
  - **current** → grey text suffixed `◆`;
  - **deleted** → grey italic text.
- **Greyed row (lost application)**: if **all** of an application's markers
  are `✗` (no live link nor `◆` left), the **whole row's background**
  turns light grey (`--color-background-secondary`) so it can be spotted at a glance.
  A row that keeps at least one live conversation is not greyed. Sorting and status
  editing stay active.
  A **mandatory** legend explains the glyph codes (`◆` current · `→` linked · `✗` deleted;
  it adapts: "clickable link" on web, "sidebar" on desktop) — required because the glyphs are mute.
- **Surface detection**: a `navigator.userAgent` containing `Electron`/`Claude`
  ⇒ desktop. `window.__SURFACE__` ("desktop"/"web") forces the rendering (tests, preference).
- **Status editing (editable mode)**: a per-row dropdown, local accumulation,
  an "N pending change(s)" bar + **Save** (a single grouped
  `sendPrompt`) / **Cancel**.
- **Read-only mode** (`--readonly`): status as a pill, no editing (ephemeral mode).
- **Localization (surface contract, LNG-2 S2 — option B)**: the HTML structure, the
  `sendPrompt` directives and the `print()` output are **English-canonical** (never
  localized). The **visible labels** default to English (`LABELS_EN`) and are localized
  by the model via `--labels-json` (interface language, **exact key set** — the script
  errors out on any missing/extra key). **Statuses** stay **canonical English** in the
  data, the engine and the `sendPrompt`; only their **display text** is localized (the
  `status_*` labels), so the `<select>`/`<option>` values remain canonical. This surface
  has **no language selector** (option B): the language is set by the model and propagated
  by the **memory-preference precedence**; the switching affordance lives on the entry
  selection widget. `--ui-lang` is accepted as metadata (no selector to pre-select here).

### Modes
- **Ephemeral**: a session view from JSON data, no persistence (`--readonly`).
- **Persistent**: from the project CSV; changes go through the write ritual.

### Write ritual (persistent, no connector)
The dashboard cannot write to the project. The Save button sends the
assistant the list of changes; the assistant runs `batch-status` (or
`upsert`), **regenerates the CSV under a unique timestamped name**, presents it
(`present_files`), and then the user **adds it to the project** and **deletes
the old version** (identified by name). Filters and sort require no
round trip.

## Refresh (DRV-5) — script-driven reconciliation
The "↻ Refresh" button asks the assistant to **rebuild/complete** the
tracker from a **scan of the project's conversations** (`conversation_search` /
`recent_chats` — project-scoped, no connector), then to pass the result to
**`manage_tracker.py reconcile`** (the logic is in the code, not in the
assistant's head — the root fix for DRV-6). See the GUIDE (workflow E) for the
full procedure. In short, the script:
- **Scope**: the assistant scans the **~100 most recent conversations** (paginated,
  adjustable, to be flagged); beyond the **floor** (oldest enumerated date), nothing
  is concluded.
- **Promotion**: `◆ → {uuid}` by **(company, position)**, in place, no duplicate.
- **Union**: a new conversation for an existing application (new UUID) is added.
- **Deletion**: `✗` marked **if and only if** a linked UUID is absent
  **and** its date is **≥ floor** (conclusive → **mandatory**); **< floor** →
  indeterminate, unchanged. *Invariant guaranteed by the code.*
- **`title`**: real captured title (display), never a key.
- **Hygiene**: a "real title ≠ canonical" report (current title / proposed / link) as a
  by-product, so the user can rename if they wish (the assistant doesn't rename).
- **Non-destructive**: manual statuses and notes preserved.
This is the mechanism that **turns dated markers into links**: without a refresh,
the Link column only shows dates.
